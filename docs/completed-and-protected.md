# Completed and protected surfaces

Treat everything listed here as **preserve-first**. Refactors and styling are fine; behaviour or output changes require explicit user approval. If a protected surface is intentionally changed, update this file in the same commit.

## Completed list

- **Accountancy** — voucher engines (Sale, Purchase, Receipt, Payment, Contra, Journal Voucher, returns, GL postings), Day Book, Trial Balance, Balance Sheet, P&L, Receivables/Payables (bill-wise), Cash/Bank Book, Ratios, GST hub + HSN classification, ledger outstandings. Don't touch math paths (`effectiveLedgerBalance`, `aggregateClosingAsOf`, `aggregateRange`, `netProfitLoss`) without an explicit accounting task. **Balance Sheet closing-stock valuation became method-aware in PR 3 of noble-boole (2026-05-28)** — the BS now reads `OrgDefaults.valuationMethod` (default `WEIGHTED_AVG`) and the UI has a dropdown to preview other methods (`LAST_INWARD | SIMPLE_AVG | FIFO | MONTHLY_AVG`); the underlying `productClosingValue` rewrote to walk `InvStockLedger` + opening master fields after the `costPaise` cache column was dropped. **2026-06-01 — credit is deny-by-default:** `checkCreditLimit` now treats `Account.creditLimit` NULL exactly like 0 (no credit); only an explicit POSITIVE limit permits a credit sale. New customers (person/company/portal-register) are created with `creditLimit: 0`, and the POS account-snapshot maps NULL→0 (no more "Unlimited"). **Note:** enforcement still lives ONLY in the POS sale path; the office Sale voucher (`/api/inventory/vouchers`) does not yet call `checkCreditLimit`. See [docs/modules/accountancy.md](modules/accountancy.md).
- **POS** — counter-based tills, shift lifecycle (open → sales → close with variance), tax-inclusive pricing default, thermal ESC/POS receipt printing, payment splits. **2026-05-31 — materialized effective sale price:** the InvProduct selling-price column was renamed `pricePaise` → `effectiveSalePricePaise` and is now a *materialized* value rewritten from `effectiveSalePriceSource` (renamed from `saleSource`; `SAVED`→`savedSalePricePaise`, `COMPUTED`→cost×margin, `STRATEGY`→engine) by `recomputePricesForProducts` after every transaction and immediately on Freeze. POS + the Sale voucher read it **raw** via `products/lookup`, which exposes it under the stable field name `pricePaise` (the boundary that keeps the shop/POS DTOs unchanged). The read-time `effectiveSellPaise()` helper was removed. **2026-06-01 — POS price re-sync:** PosScreen now re-fetches prices once when a sale starts (a customer is picked) via the new lightweight `GET /api/inventory/products/prices` (id + `effectiveSalePricePaise` + `mrpPaise` only — no GST/cost cascade), so a counter idle for hours picks up prices re-frozen meanwhile. It patches the in-memory list by id; cart lines stay snapshotted so a sale in progress is never repriced. **2026-06-01 — shift-close payment breakdown:** the Close-shift dialog, post-close report and thermal printout now show a "Payments collected this shift" tally across ALL methods (Cash, UPI, Card, Wallet, Cheque, Bank Transfer — only those with activity, custom per-counter labels honoured), derived at read-time from `InvVoucherTender` + RECEIPT debits per the counter's routing accounts (`buildShiftTenderBreakdown` in `shiftMath.ts`); the tally is informational (cash reconciliation/variance math unchanged). The dialog is now full-screen with a per-denomination note/coin counter feeding the physical count, and it no longer closes on outside-click/Escape (only Cancel/Done/✕). The denomination list is org-configurable (country-specific) via `OrgDefaults.cashDenominationsJson`, edited in Settings → Org Defaults and read by the dialog through `getOrgDefaults()` (falls back to the Indian default set). **GL fix (same change):** the closing Contra now sweeps `declared + drops − carryOver` (was `declared − carryOver`), so mid-shift cash drops to the safe are settled to the Vault at close instead of being stranded in the counter till GL — the till now closes at exactly the carry-over. **2026-06-01 — POS counter expenditure:** the POS top bar's **Exp** button opens `PosExpenditureDialog` to record a small cash expense paid from the drawer (tea, sundry donation). It posts a **PAYMENT voucher** `Dr <EXPENSE-group ledger> / Cr counter till` via `POST /api/pos/shifts/[id]/expenditures` (funding locked to the shift's counter till), stores a `PosExpenditure` row, and the shift-close **expected drawer subtracts expenditures**. **Per-counter allow-list:** `PosCounter.allowedExpenseAccountIds` (number[], edited at `/office/admin/counters`) restricts which EXPENSE ledgers a counter may spend to — empty = no restriction (all); the Exp dialog loads the allowed list from `GET /api/pos/shifts/[id]/expense-accounts` and the POST rejects anything outside it (`computeExpectedCash(opening, cashSales, drops, expenditures)`) so the drawer reconciles and the expense isn't double-booked as Cash Short. New schema: `PosExpenditure` (+ `hard-clean` `pos_expenditures`). **2026-06-01 — Rcv receipt + counter visibility:** a **Rcv** button posts a RECEIPT voucher (Dr counter till / Cr party) via `postReceiptVoucher` to collect a party payment; receipts/expenditures now stamp the shift's branch on their JournalLine (`branchId`), which the GL vouchers endpoint (`/api/accountancy/vouchers`) now derives + returns so the **Day Book shows the branch** for them. A **Cash In/Out** tab on `/vouchers/pos` lists counter receipts + expenditures (`/api/pos/cash-movements`). Receipts are shift-linked via the new `PosReceipt` table (+ `hard-clean` `pos_receipts`). Both Rcv + Exp open a printable thermal voucher at `/receipt/payment/[id]`. **2026-06-01 — large-cart timeout fix:** the POS sale (`/api/pos/sale`) and both return routes (`/api/pos/return`, `/api/pos/return/lost`) do voucher + GL post + per-line stock movement (~3 sequential DB round-trips/line) in ONE interactive transaction; carts of 10+ items blew past Prisma's 5s default and expired mid-sale ("query cannot be executed on an expired transaction"). All three now pass `{ timeout: 30_000, maxWait: 10_000 }` (matching the office voucher post route) — no math/output change, just a wider window. The lost-invoice tab was also removed from `PosReturnDialog` (dialog is now two-tab; the `/api/pos/return/lost` endpoint stays for API use). **2026-06-01 — return GST-balance fix:** both return routes stored a *goods-only* `subtotal` on the SALE_RETURN voucher, but `postInvVoucherToGl` treats `voucher.subtotal` as **tax-inclusive** (`goodsAmount = subtotal − taxAmount`). For any taxed item the bridge double-subtracted the GST, the credit note came out short by exactly the tax, and the JE was rejected as unbalanced ("GL bridge could not build a journal entry") — so returns of GST items were fully broken. Both routes now store a tax-inclusive `subtotal` (goods + tax) and tax-inclusive line amounts, matching the SALE/POS convention (stock valuation still uses qty×rate). **Pending:** POS return flow (multi-partial-return guard). See [docs/modules/pos.md](modules/pos.md).
