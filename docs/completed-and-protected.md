# Completed and protected surfaces

Treat everything listed here as **preserve-first**. Refactors and styling are fine; behaviour or output changes require explicit user approval. If a protected surface is intentionally changed, update this file in the same commit.

## Completed list

- **Accountancy** — voucher engines (Sale, Purchase, Receipt, Payment, Contra, Journal Voucher, returns, GL postings), Day Book, Trial Balance, Balance Sheet, P&L, Receivables/Payables (bill-wise), Cash/Bank Book, Ratios, GST hub + HSN classification, ledger outstandings. Don't touch math paths (`effectiveLedgerBalance`, `aggregateClosingAsOf`, `aggregateRange`, `netProfitLoss`) without an explicit accounting task. **Balance Sheet closing-stock valuation became method-aware in PR 3 of noble-boole (2026-05-28)** — the BS now reads `OrgDefaults.valuationMethod` (default `WEIGHTED_AVG`) and the UI has a dropdown to preview other methods (`LAST_INWARD | SIMPLE_AVG | FIFO | MONTHLY_AVG`); the underlying `productClosingValue` rewrote to walk `InvStockLedger` + opening master fields after the `costPaise` cache column was dropped. **2026-06-01 — credit is deny-by-default:** `checkCreditLimit` now treats `Account.creditLimit` NULL exactly like 0 (no credit); only an explicit POSITIVE limit permits a credit sale. New customers (person/company/portal-register) are created with `creditLimit: 0`, and the POS account-snapshot maps NULL→0 (no more "Unlimited"). **Note:** enforcement still lives ONLY in the POS sale path; the office Sale voucher (`/api/inventory/vouchers`) does not yet call `checkCreditLimit`. See [docs/modules/accountancy.md](modules/accountancy.md).
- **POS** — counter-based tills, shift lifecycle (open → sales → close with variance), tax-inclusive pricing default, thermal ESC/POS receipt printing, payment splits. **2026-05-31 — materialized effective sale price:** the InvProduct selling-price column was renamed `pricePaise` → `effectiveSalePricePaise` and is now a *materialized* value rewritten from `effectiveSalePriceSource` (renamed from `saleSource`; `SAVED`→`savedSalePricePaise`, `COMPUTED`→cost×margin, `STRATEGY`→engine) by `recomputePricesForProducts` after every transaction and immediately on Freeze. POS + the Sale voucher read it **raw** via `products/lookup`, which exposes it under the stable field name `pricePaise` (the boundary that keeps the shop/POS DTOs unchanged). The read-time `effectiveSellPaise()` helper was removed. **2026-06-01 — POS price re-sync:** PosScreen now re-fetches prices once when a sale starts (a customer is picked) via the new lightweight `GET /api/inventory/products/prices` (id + `effectiveSalePricePaise` + `mrpPaise` only — no GST/cost cascade), so a counter idle for hours picks up prices re-frozen meanwhile. It patches the in-memory list by id; cart lines stay snapshotted so a sale in progress is never repriced. **2026-06-01 — shift-close payment breakdown:** the Close-shift dialog, post-close report and thermal printout now show a "Payments collected this shift" tally across ALL methods (Cash, UPI, Card, Wallet, Cheque, Bank Transfer — only those with activity, custom per-counter labels honoured), derived at read-time from `InvVoucherTender` + RECEIPT debits per the counter's routing accounts (`buildShiftTenderBreakdown` in `shiftMath.ts`); the tally is informational (cash reconciliation/variance math unchanged). The dialog is now full-screen with a per-denomination note/coin counter feeding the physical count, and it no longer closes on outside-click/Escape (only Cancel/Done/✕). The denomination list is org-configurable (country-specific) via `OrgDefaults.cashDenominationsJson`, edited in Settings → Org Defaults and read by the dialog through `getOrgDefaults()` (falls back to the Indian default set). **GL fix (same change):** the closing Contra now sweeps `declared + drops − carryOver` (was `declared − carryOver`), so mid-shift cash drops to the safe are settled to the Vault at close instead of being stranded in the counter till GL — the till now closes at exactly the carry-over. **2026-06-01 — POS counter expenditure:** the POS top bar's **Exp** button opens `PosExpenditureDialog` to record a small cash expense paid from the drawer (tea, sundry donation). It posts a **PAYMENT voucher** `Dr <EXPENSE-group ledger> / Cr counter till` via `POST /api/pos/shifts/[id]/expenditures` (funding locked to the shift's counter till), stores a `PosExpenditure` row, and the shift-close **expected drawer subtracts expenditures**. **Per-counter allow-list:** `PosCounter.allowedExpenseAccountIds` (number[], edited at `/office/admin/counters`) restricts which EXPENSE ledgers a counter may spend to — empty = no restriction (all); the Exp dialog loads the allowed list from `GET /api/pos/shifts/[id]/expense-accounts` and the POST rejects anything outside it (`computeExpectedCash(opening, cashSales, drops, expenditures)`) so the drawer reconciles and the expense isn't double-booked as Cash Short. New schema: `PosExpenditure` (+ `hard-clean` `pos_expenditures`). **2026-06-01 — Rcv receipt + counter visibility:** a **Rcv** button posts a RECEIPT voucher (Dr counter till / Cr party) via `postReceiptVoucher` to collect a party payment; receipts/expenditures now stamp the shift's branch on their JournalLine (`branchId`), which the GL vouchers endpoint (`/api/accountancy/vouchers`) now derives + returns so the **Day Book shows the branch** for them. A **Cash In/Out** tab on `/vouchers/pos` lists counter receipts + expenditures (`/api/pos/cash-movements`). Receipts are shift-linked via the new `PosReceipt` table (+ `hard-clean` `pos_receipts`). Both Rcv + Exp open a printable thermal voucher at `/receipt/payment/[id]`. **2026-06-01 — large-cart timeout fix:** the POS sale (`/api/pos/sale`) and both return routes (`/api/pos/return`, `/api/pos/return/lost`) do voucher + GL post + per-line stock movement (~3 sequential DB round-trips/line) in ONE interactive transaction; carts of 10+ items blew past Prisma's 5s default and expired mid-sale ("query cannot be executed on an expired transaction"). All three now pass `{ timeout: 30_000, maxWait: 10_000 }` (matching the office voucher post route) — no math/output change, just a wider window. The lost-invoice tab was also removed from `PosReturnDialog` (dialog is now two-tab; the `/api/pos/return/lost` endpoint stays for API use). **2026-06-01 — return GST-balance fix:** both return routes stored a *goods-only* `subtotal` on the SALE_RETURN voucher, but `postInvVoucherToGl` treats `voucher.subtotal` as **tax-inclusive** (`goodsAmount = subtotal − taxAmount`). For any taxed item the bridge double-subtracted the GST, the credit note came out short by exactly the tax, and the JE was rejected as unbalanced ("GL bridge could not build a journal entry") — so returns of GST items were fully broken. Both routes now store a tax-inclusive `subtotal` (goods + tax) and tax-inclusive line amounts, matching the SALE/POS convention (stock valuation still uses qty×rate). **2026-06-02 — customer "Today's discount" price ladder:** the printed receipt (thermal `B` density + A4 `C` density via `ThermalReceiptPreview`/`A4InvoicePreview`) and the live QR/thermal relays now present a customer-facing price ladder — per-line MRP + barcode, with every reduction pooled into a "Today's discount" block (price-benefit = barcode→effective, tier, loyalty, coupon), a "You saved ₹X (Y%)" hero, and a net-of-discount **HSN/rate-wise** tax summary (gated by `template.showTaxSummary`). The per-item *real* selling price is never shown, so a multi-item receipt doesn't reveal it (anti-competitor). This is a **computed view** — a new pure helper `src/modules/pos/lib/priceLadder.ts` (`computePriceLadder`) derives it from the real voucher; nothing obfuscated is persisted, so edits/returns just re-compute. **Accounting math is unchanged** (subtotal/tax/total flow as before; the ladder distributes the bill discount proportionally per line only to build the display HSN summary, which reconciles to the paid total). **New snapshot:** POS sale lines now persist `mrpPaise` + the new `InvVoucherLine.savedSalePricePaise` (barcode) at sale time (`/api/pos/sale` + `PosScreen`), since the receipt is DB-driven and product prices drift. **B2B:** the buyer's GSTIN prints when the party has one. The QR (`qrDisplay.cart`) + thermal `localhost:9191/print/pos` payloads carry the new fields **additively** — the external relays (9191/9192) must be updated to render them; old relays ignore them. **2026-06-03 — thermal relay now respects the template + ladder:** `tools/thermal-relay/relay.js` `buildPosBuffer` was rewritten so the printed POS slip matches `/receipt/invoice/[id]?kind=POS` — it reads a `template` field (resolved POS `VoucherPrintTemplate`, returned by `/api/pos/sale` as `posTemplate` and forwarded by `PosScreen`) for the header/address/toggles/terms/footer, and renders the "Today's discount" ladder (tag line total + struck MRP → Gross → discounts → GST → Total → "You saved") instead of the old hardcoded "TAX INVOICE" + Subtotal/Tax/Total. Falls back to the legacy layout when no template/ladder is sent; ESC/POS hardware limits remain (monospace font, no rastered logo). **2026-06-03 — overpayment / collect-on-the-go (behaviour change):** the POS sale (`/api/pos/sale`) is no longer strictly exact-pay. When the customer tenders MORE than the bill and a customer is attached, the cashier confirms with `collectSurplus: true`: the **sale voucher stays exactly at the bill** but is settled by a single **AR tender** (Dr Customer / Cr Sales+GST), and the FULL money inflow rides a separate **Receipt voucher** at its real tender ledgers (cash→till, UPI→upi, …) so the bank/UPI statement still matches one voucher 1:1. The receipt is allocated **FIFO**: this sale's JE first, then the customer's oldest open bills, leftover = customer advance (unallocated AR credit). Under-pay is still rejected (→ `/sale`); walk-ins (no person/company account) and gift-card redemptions are rejected for surplus. New: `postReceiptVoucher` accepts `allocations[]` (multi-bill) with an over-allocation guard; `outstandings.ts` adds `getOpenSaleBillsForFifo` (oldest-first, tx-aware). Cashier-side cart lines now also show a read-only **barcode** price beside MRP. **Document split:** on a surplus sale the POS **invoice** prints as a clean sale (no tender/payment lines — the sale is AR-settled) and the **Receipt voucher** (`/receipt/payment/[id]`, auto-opened on Confirm+Print) carries the full **tender breakdown** (cash/UPI/… one row each) + the arrear/advance narration; exact-pay sales still print tenders on the POS slip the traditional way. **Accounting math paths unchanged** (`postInvVoucherToGl`, `effectiveLedgerBalance`, `aggregateClosingAsOf`, `netProfitLoss`) — only the tender shape and an additive Receipt-voucher flow were added. **2026-06-03 — relay-aware reprints + register print buttons:** the POS receipt pages are now relay-first. `/receipt/invoice/[id]?kind=POS` and `/receipt/payment/[id]` render a `ThermalAutoPrint` toolbar (replaces `ReceiptButtons` on the POS thermal surfaces only — office A4 `kind=SALE` keeps the browser `ReceiptButtons`) that POSTs to the thermal bridge by default (`/print/pos` resp. `/print/payment`, payload built server-side on the page) and falls back to `window.print()` when the relay is offline. The relay's `buildPaymentBuffer` gained `title/partyLabel/totalLabel` so it prints both RECEIPT ("Received") and PAYMENT ("Paid") vouchers. The `/vouchers/pos` register now has a **Print** action on every row across all three tabs (Sales → `/receipt/invoice?kind=POS`, Cash In/Out → `/receipt/payment/[voucherId]` (cash-movements API now returns `voucherId`), Cash Book → existing link), each opening the relay-aware page. **2026-06-08 — POS sale edit-mode + lifecycle parity:** posted POS sales now reopen in `PosScreen` itself (`/vouchers/pos/new?voucherId=`, routed via `voucherFormUrls.POS`) instead of the office Sales form — which silently dropped the POS-specific charge rows (loyalty / coupon / gift-card) on save, corrupting the Balance Sheet. Edit-mode hydrates customer + cart, then `PATCH /api/inventory/vouchers/[id]` sending **lines + the re-sent original charges + discount/shipping/round-off** and **omitting tenders**, so payment + offer rows are preserved and the GL re-posts faithfully (a reduced total over the unchanged payment becomes a customer AR credit). Same change fixed the lifecycle: type `POS` was missing from the `isSale` stock-reversal in the voucher **edit (PATCH), cancel, delete and hard-delete** endpoints — so they reversed the GL but never restored stock (inventory asset wrong); `POS` is now included in all four (mirrors `SALE`; `postInvVoucherToGl` already treats `POS` as a sale). **Caveat:** the screen still shows its *live* recomputed total in edit mode, which can differ from the saved total (original offers are preserved, not re-derived) — ledger is correct; the on-screen figure is the rough edge. **Accounting math paths unchanged.** Browser/ledger verification pending. **Pending:** POS return flow (multi-partial-return guard). See [docs/modules/pos.md](modules/pos.md).
