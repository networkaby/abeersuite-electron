## Executive summary

The codebase is functionally mature, but the v5.0.4 move to **local-write counters** exposes a structural hole the sync layer was never designed for: cumulative cache columns (`Account.balance`, `VoucherSeries.nextSeq`, `GiftCard.balance`, stock) are shipped as whole-row images under last-write-wins, so any two writers silently overwrite each other's increments — ledger drift, re-used voucher numbers and double-spent gift cards are the shipped default, not an edge case. Alongside that, the API layer has a consistent RBAC gap: roughly a dozen mutating routes (all `settings/**` writes, voucher-series reset, inventory voucher PATCH, the legacy `/api/sync/push`) trust `requireAuth()` alone, and two user/role endpoints let a mid-tier `users:edit` or `roles:edit` holder promote themselves to full admin. Accounting-integrity bugs in the online-order receipt allocation (wrong table lookup) and POS cancel (rewards never reversed) are silently mis-stating receivables and gift-card liability in production today. The new desktop backup/restore is welcome but runs `pg_restore --clean` against the pgBouncer transaction pooler on every packaged install and does not stop/re-seed the replica. Seeds and docs show only low-severity drift; the code contract in `hard-clean.ts` is the one seed item worth fixing.

**Fix first, in this order:**
1. **Sync of cumulative caches (critical)** — stop pushing `balance`/`nextSeq`/`stock` row images; recompute on the receiving side or push deltas; key `VoucherSeries` per counter.
2. **RBAC sweep (3 highs)** — `requirePermission(SETTINGS_MANAGE)` on every `settings/**` write; rank/self guards on `users/[id]/roles` and `users/[id]/permissions`; delete `/api/sync/push`.
3. **Two silent accounting bugs (2 highs)** — invoice route reads the receipt from `UniversalVoucher` not `VoucherDetail`; POS cancel reverses gift-card/coupon/loyalty inside the same tx.

## A. Sync & multi-writer integrity (money / data loss)

### A1. ~~CRITICAL~~ FIXED (2026-09-05, `c2ad64b3` + `0cac37f8`) — Counter-local writes push whole-row images of cumulative caches under last-write-wins
**File:** `src/shared/lib/sync/push.ts:248-277`; trigger `resources/local-schema.sql:5729-5765`
**Why:** `_outbox_capture` stores `to_jsonb(NEW)` and push does `upsert({update: payload})` with only an `updatedAt` skip guard. A counter increments `Account.balance` / `VoucherSeries.nextSeq` / `GiftCard.balance` / `InvProduct` stock on its replica from the last-pulled value and overwrites Supabase, discarding every increment the office or another counter made in between. `effectiveLedgerBalance` reads the cache, so Balance Sheet drifts silently; `nextSeq` regression re-issues voucher numbers; gift cards get spent twice.
**Fix:** Exclude cumulative columns from pushed payloads and recompute on receive (`recomputeAccountBalances`, `recomputeProductStock`), or push deltas; key `VoucherSeries` by `(kind, counterNumber)`; run recompute after each pull/push cycle.
**Done:** `cacheColumns` in `prisma/sync-tables.json` drives the capture trigger, `push.ts` (UPDATE half only) and `pull.js`; each side re-sums from its own ledger (`rebuildTotals.ts` / `sync-engine/lib/rebuildTotals.js`). See roadmap §4.4.

### A2. ~~HIGH~~ FIXED (2026-09-05, `8c660653` + the legacy-path follow-up) — Voucher numbering duplicates: SALE_RETURN/office kinds pass no `counterNumber` and `VoucherSeries` is one LWW-synced row
**File:** `src/modules/accountancy/lib/balance.ts:142-200`; `voucherRef.ts:85-86`; callers `pos/return/route.ts:206`, `pos/return/lost/route.ts:128`, `posQuoteVoucher.ts:159`, `inventory/vouchers/route.ts:576`
**Why:** Only `pos/sale` threads the counter number; everything else defaults to 1, so two machines mint identical credit-note numbers from the same pulled `nextSeq`. No unique index on `voucherNo` catches it — duplicates reach printed GST documents.
**Fix:** Thread `counterNumber` into every `invNextRef`/`engineCreateVoucher` call; reserve a counter number for the office; per-counter series rows or exclude `nextSeq` from sync; partial unique index on `(type, voucherNo) WHERE status <> 'DRAFT'`.
**Done:** `VoucherSeriesCounter (kind, counterNumber)` — only the machine numbering on a row writes it; `resolveCounterNumber()` defaults from this PC's `counter-setup.json`, so no caller had to change; counter 1 is reserved for the office. The legacy calendar-year fallback in `stock.ts` (`POS_ESTIMATE`/`POS_ORDER`/`ONLINE_*`) was missed by the first pass and now uses the same resolver. The partial unique index is still **not** added — run `pnpm check:voucher-duplicates` first.

### A3. ~~MEDIUM~~ FIXED (2026-09-05) — Restore replaces Supabase but leaves the counter replica and sync worker running
**File:** `electron/main.ts:637-656`; `electron/backupManager.ts:308-336`
**Why:** Restored rows carry older `updatedAt` than the watermark so are never pulled (and lose LWW when they are); key-only reconcile never repairs rolled-back values; pending outbox rows push newer data back over the restore.
**Fix:** `stopSyncWorker()` → `runRestore` → `wipeReplica()` + reset cursors/outbox → restart; tell the operator other counters must re-seed.
**Done:** that, plus the two writers the finding missed — an in-flight `sync-once` child (`stopSyncWorker()` does not wait) and the outbox flusher inside the forked Next server (no channel from main). `app.relaunch()` + `app.quit()` reaches all three. The card now names the pending-write count (`countPendingOutbox`) and says other counters must be re-onboarded. See roadmap §4.5.

## B. Security / RBAC

> ⏸️ **WHOLE SECTION DEFERRED — owner's decision, 2026-09-05.** Permissions are page-level for this phase. The settings pages and `office/admin/counters` are permission-gated in the nav, so a cashier cannot reach them; stronger API-level gating is planned for after the dev version is complete. Every B finding below is accurate and none is disputed — they are simply **not** to be actioned or re-raised until that phase starts. **B4 is the one exception in kind:** it is a credential leak, not a permission gap, and stays open.

### B1. HIGH — Settings write APIs gated by `requireAuth()` only
**File:** `src/app/api/settings/credit-limit/route.ts:17` (+ `org-defaults:28`, `offline-policies:38`, `payment-methods/[id]:29,107`, `couriers/[id]:31,61`, `customer-groups`, `pos-services`, `voucher-templates/[kind]:36`, `[kind]/reset:15`)
**Why:** Any cashier can switch live payment gateway/environment, change the settlement ledger every sale posts to, disable offline restraints, alter credit limits and print templates via direct POST. Sidebar hiding is the only gate; `/api` is excluded from `proxy.ts`.
**Fix:** `requirePermission(PERMISSIONS.SETTINGS_MANAGE)` on every mutating handler under `settings/**` (key already exists, no migration).

### B2. HIGH — `users:edit` holder can assign any role / grant any permission to anyone, including self
**File:** `src/app/api/users/[id]/roles/route.ts:46`; `src/app/api/users/[id]/permissions/route.ts:74-88`
**Why:** The rank guard in `users/[id]/route.ts:170-181` is bypassed by these sub-routes. Seeded Branch Manager (R2, `users:edit`) can PUT own role → R1 or GRANT `admin:bypass` and become full admin.
**Fix:** Apply the same rank guard to roles PUT; in permissions POST reject self-target, reject `systemOnly` ids and any id the caller does not hold.

### B3. HIGH — `/api/sync/push` lets any staff upsert arbitrary rows in every syncable table
**File:** `src/app/api/sync/push/route.ts:47`; `push.ts:220-279`
**Why:** `requireAuth` only; `tableName` is any string in the 116-table registry, payload is the full row image, LWW guard bypassed by a future `updatedAt`. Ledger, vouchers, shifts, gateway config rewriteable on Supabase. Flusher no longer uses it — pure attack surface, already noted "tracked separately" in the route header.
**Fix:** Delete the route; if kept, counter-specific credential plus id-block ownership check.

### B4. HIGH — Production DB URL with password sent as a GitHub workflow input and echoed in run logs
**File:** `src/app/api/settings/backup/route.ts:53`; `src/app/api/cron/backup/route.ts:49-56`; `.github/workflows/backup.yml:49`
**Why:** Every backup writes the Supabase superuser string into Actions logs; `docs/production-cleanup.md` already admits it is burned in historical logs; counter builds ship a `GITHUB_DISPATCH_TOKEN` with Actions read+write, so a till PAT recovers the DB password.
**Fix:** Drop `source_db_url` input; workflow reads `secrets.DIRECT_DATABASE_URL`; rotate the password.
**Withdrawn in part (2026-10-24):** the owner keeps `source_db_url` — two Vercel projects share one backup repo and only the app knows which database to dump (`KEEP THIS BLOCK` in both routes); the backup repo stays private. Done: restore masks its typed target URL. **Left:** rotate the password.

### B5. MEDIUM — `roles:edit` holder can grant any permission to their own role
**File:** `src/app/api/roles/[id]/permissions/route.ts:36,106-110`; `roles/[id]/route.ts:54-100`
**Why:** All-access department → no pool filter; PATCH lets the caller re-home the role to DEP-ADMIN and set rank 100 first. Escalation from role editor to owner.
**Fix:** Refuse edits to own role or rank ≥ caller; strip `systemOnly` ids; require `settings:manage` for admin-tier keys.

### B6. MEDIUM — Any staff can reset voucher numbering series (and run recompute-balances)
**File:** `src/app/api/accountancy/voucher-series/[kind]/reset/route.ts:11`; `[kind]/route.ts:30`; `maintenance/recompute-balances/route.ts:17`
**Why:** Resetting `nextSeq` mid-year yields duplicate invoice/GST numbers from a cashier session. (Recompute alone would be low — it repairs, not corrupts.)
**Fix:** `requirePermission(ACCOUNTANCY_MASTERS_EDIT)` on all three.

### B7. MEDIUM — Inventory voucher PATCH and DRAFT DELETE have no per-kind permission check
**File:** `src/app/api/inventory/vouchers/[id]/route.ts:126` (PATCH), `:520` (DELETE)
**Why:** Contract "who can cancel can edit" (`permissions.ts:62,222`) not enforced; a clerk with only create/post can rewrite lines/party/amounts of any POSTED voucher (stock+GL reversed and re-posted). Body is also unvalidated.
**Fix:** `userCanVoucherKind(user, type, "cancel")` on PATCH, `"delete"` on DELETE; reuse the create zod schema.

### B8. MEDIUM — Journal-entry hard-delete gated on `admin:bypass` — unusable by any real Admin
**File:** `src/app/api/accountancy/journal-entries/[id]/hard-delete/route.ts:20`
**Why:** `admin:bypass` is the env-only sentinel (systemOnly); every seeded Admin gets 403 while the UI shows the button. Fails closed, so a broken feature not an exposure.
**Fix:** `requireAuth()` + `userCanVoucherKind(user, "JOURNAL", "delete")`, like vouchers hard-delete.

### B9. MEDIUM — Cron endpoints fail open when `CRON_SECRET` is unset; `backup-due` mutates state
**File:** `src/app/api/cron/backup-due/route.ts:26`; `cron/backup/route.ts:23-26`
**Why:** Unauthenticated callers can stamp `lastRunAt` hourly (suppress real backups) or trigger unbounded workflow runs each leaking the DB URL (B4). `production-cleanup.md` says Vercel is currently the missing side.
**Fix:** Fail closed when the secret is missing; log a startup warning.

### B10. LOW — Electron backup/restore/counter IPC handlers do no permission check in main
**File:** `electron/main.ts:606,614,634,546,453`; `preload.ts:100-120`
**Why:** Exposed to every renderer page including `/staff/login`; devtools open in packaged builds; no `will-navigate` guard. Attacker at the keyboard already owns `.env`, so convenience not new capability.
**Fix:** Verify `settings:manage` via the local Next API before dump/restore; disable devtools in packaged builds; add `will-navigate` origin guard.
**Done in part (2026-10-24):** the `will-navigate` / `will-redirect` origin guard (a workflow "navigate" action could load any URL in the main window). The permission check and devtools stay deferred with section B.

### B11. LOW — Parked Razorpay webhook writes payment ids with no signature verification
**File:** `src/app/api/shop/razorpay/webhook/route.ts:18`
**Why:** Anyone with an order id can overwrite/null the legitimate `razorpayPaymentId`; `PROJECT_BRAIN.md:651` claims `RAZORPAY_WEBHOOK_SECRET` gates it — code never reads it. Shipway/Shiprocket webhooks are fail-open when token env is blank.
**Fix:** HMAC-verify `x-razorpay-signature`, or return 404 while parked; make webhook tokens required in production.

### B12. LOW — Self password change does not require the current password; sessions not revoked
**File:** `src/app/api/users/[id]/password/route.ts:27`
**Why:** Unlocked till → permanent account takeover. Portal route already does this correctly (`portal/password/route.ts:31`).
**Fix:** Require and verify `currentPassword` on self path; `revokeUserSessions(userId)` after.

## C. Accounting integrity

### C1. ~~HIGH~~ FIXED (2026-09-05, `7f566504`) — Online invoice looks up the gateway RECEIPT in `VoucherDetail` (wrong table) — never allocates, or allocates an unrelated voucher
**File:** `src/app/api/ecommerce/orders/[id]/invoice/route.ts:556-561`; same bug in `orders/[id]/return/route.ts:308-313`
**Why:** `receiptVoucherId` is a spine id; RECEIPTs have no `VoucherDetail` row. Null → allocation silently skipped, invoice open + unallocated advance forever (receivables overstated). Id collision → an unrelated sale's `totalAmount` allocated. Every paid online order.
**Fix as shipped:** the suggested fix above was itself wrong — `UniversalVoucher` has **no `totalAmount` column** (`prisma/schema/finance.prisma`); a financial voucher's total is the sum of its DEBIT legs. So: new `voucherDebitTotal(tx, spineId)` in `transactionEngine.ts` next to `engineCreateVoucher`, which applies the same rule at creation. The invoice route now reads the spine guarded on `type: "RECEIPT", status: "POSTED", deletedAt: null` — a stale id can no longer allocate an unrelated voucher's money — and takes the total from that helper. The return route's lookup was deleted outright: `receiptVoucherId` already **is** the spine id `spawnShopRefund` wants (`getRefundForPayout` reads it back off `UniversalVoucher`), so it is passed straight through.

**Backfill:** orders invoiced between 2026-07-22 (`f6ca24a8`, when the bug shipped) and this fix still carry a missing or wrong `VoucherAllocation`; the code fix does not repair history. `pnpm backfill:receipt-allocations` reports them and writes nothing; `--fix` applies the repair. Idempotent, and it only ever touches allocations whose source is a POSTED RECEIPT spine that an ONLINE_INVOICE points at. Two cases it refuses to guess at and leaves for a human: a `receiptVoucherId` that is not a posted RECEIPT spine, and a receipt already allocated to some other live voucher. **Not yet run against any database** — see the note in `## Status log`.

### C2. ~~HIGH~~ FIXED (2026-09-05, `1ca36ab3` + this commit) — Cancelling a POSTED POS sale does not reverse gift-card draw, coupon redemption or loyalty
**File:** `src/app/api/inventory/vouchers/[id]/cancel/route.ts:46-100`; `pos/return/route.ts` (no gift-card refund path)
**Why:** GL liability credit is reversed but `GiftCard.balance`/REDEEM txn stay — card owner loses value with no ledger backing. Coupon stays used, loyalty lots stay credited/consumed. `refundGiftCard` has zero callers; returns of gift-card-paid goods pay out real cash.
**Fix:** In cancel tx call `reverseCouponRedemption`, `reverseLoyaltyForReturn`, `refundGiftCard` for the spine; add a GIFT_CARD refund mode to `pos/return`.
**Done:** both halves. Cancel now refunds every REDEEM `GiftCardTxn` on the spine, frees the coupon and reverses loyalty inside the same tx — `refundGiftCard` had no caller at all before this. `ensureCancelable` does not block a sale that already has returns, so the partial-return-then-cancel case was checked: the claw-back caps at the earn lot's remaining points and the restore at the original redeem net of prior returns, so it reverses once. `pos/return` gained a `GIFT_CARD` refund mode — the Cr leg goes to the Gift Card Liability ledger the sale debited and `refundGiftCard` puts the value back on the card, recorded against the credit note's spine. New `giftCardRefundableForSale()` is the single definition of what is still refundable (draw net of refunds on the sale AND its returns); the return-search endpoint computes the same in batch so the dialog can offer the option.
**Left:** a MIXED-tender return (part card, part cash) is refused for `GIFT_CARD` with the cap named, rather than split across two tenders. Splitting needs a refund-mode-per-tender UI — a separate item.

### C3. ~~MEDIUM~~ FIXED (2026-09-05, `c2ad64b3` + this commit) — Gift card can be over-drawn / double-spent
**File:** `src/modules/coupons/lib/giftCard.ts:34-38`; `pos/sale/route.ts:757-766` (balance read outside tx)
**Why:** `newBal` written unconditionally, no `>= 0` check, no conditional update, no idempotency key, no DB CHECK. Two tills or a double-submit both redeem the full balance. (Cross-counter case is the normal case under A1.)
**Fix:** `updateMany({ where:{ id, status:"ACTIVE", balance:{gte:amount} }, data:{ balance:{decrement:amount} } })` and 409 on `count===0`; compute redeem amount inside the tx.
**Done:** the draw is conditional in one statement (`c2ad64b3`), and `refundGiftCard` now lets the database do the addition the same way. It used to read the balance, add, then write it back, so two overlapping refunds of one card both read the same starting figure and one addition was lost — the two `GiftCardTxn` rows survived, so the history and the card disagreed, and `recomputeGiftCardBalances` only runs on the sync path, so an office-only database never repaired it. Unreachable until C2 gave that function its first callers.
**Owner's decision (2026-09-05), the other two residuals:** gift cards are not used offline, so two counters cannot over-draw one card; and computing the redeem amount outside the tx is accepted — the 409 makes the cashier re-scan, a small delay online/local is fine, and staff have been instructed.

### C4. MEDIUM — Hard-delete/restore/edit paths resolve ledger nature without the group fallback — null-`normalBalance` party ledgers drift `Account.balance`
**File:** `src/modules/accountancy/lib/auditRestore.ts:110-121`; `journal-entries/[id]/hard-delete/route.ts:33-46`; `journal-entries/[id]/route.ts:91-136`; `accountancy/vouchers/[id]/route.ts:115-160`
**Why:** Party ledgers are created with null `normalBalance`; the engine uses `defaultNormalBalanceForGroupType`, these paths skip or mis-sign. Restored receipt never re-applies to the customer; JE hard-delete decrements with wrong sign. Cache feeds `effectiveLedgerBalance`.
**Fix:** Use `loadNormalBalances(tx, ids)` (already in `balance.ts`) on all four paths.

### C5. MEDIUM — Loyalty discount granted even when fewer points are consumed than priced
**File:** `src/app/api/pos/sale/route.ts:1053-1066`; `applyLoyalty.ts:58-75,137-148`
**Why:** Balance read pre-tx; `consumeLotsFIFO` silently returns `consumed <= points`; no check that `pointsRedeemed === redeemPoints`. Second racing sale gets full rupee discount and full GL leg with zero points burned.
**Fix:** Throw `LifecycleError(409)` in tx when `loyaltyResult.pointsRedeemed < redeemPoints`; or clamp from `liveBalance(tx, ...)`.

### C6. LOW — `markOrderPaid` check-then-update is not atomic
**File:** `src/modules/order/lib/markOrderPaid.ts:55-66`
**Why:** Overlapping verify/callback both pass the status check and both post the advance RECEIPT. Narrow window (no server-to-server path races the client).
**Fix:** `updateMany({ where:{ ticketId, legacyStatus:"PENDING_PAYMENT" } })`, proceed only if `count===1`.

### C7. LOW — `RedemptionHold` rows are created but never executed or released
**File:** `src/app/api/pos/order/route.ts:107-110`; `redemptionHold.ts:77,102` (no callers)
**Why:** Write-only table of permanently HELD rows; foundation note overstates what is wired. No live GL effect.
**Fix:** Reject `body.redemptions` until the apply slice ships, or wire execute/release into fulfil/cancel.
