# Repo Audit Report — service-mgmt-experiment (`dev`)

_Generated 2026-06-09 via multi-agent workflow (24 agents, 5 dimensions, adversarial verification). Mechanical baselines: `tsc --noEmit` clean; `seed:check-docs` = 5 broken doc paths + 6 stale module docs._

## Executive summary

The repo is in good structural health: accounting totals (Trial Balance, Balance Sheet, P&L) remain internally consistent, the protected math paths are untouched, and the verified findings are dominated by documentation drift rather than broken core logic. The two genuinely serious issues are both at the edges: an unauthenticated, ownership-unchecked Razorpay order-init endpoint (IDOR + cost/DoS amplifier), and a money-affecting regression where editing a POS Order silently drops loyalty/coupon discounts and overcharges the customer. A cluster of accounting-correctness defects in the freshly-shipped Refund (P9) path are individually low-to-medium and bounded (per-ledger attribution and idempotency, not total corruption), but they share a root cause — fragile free-text/single-ledger refund resolution — and deserve a coordinated fix. The largest volume of findings is the O2C Orders/Delivery/Refund surface shipping with zero module documentation and stale status/invariants in `PROJECT_BRAIN.md` and `sales.md`, which will actively mislead the next agent.

**Top 3 to fix first:**
1. **Add auth + ownership check to the Razorpay order-init endpoint** (`shop/orders/[id]/razorpay/route.ts`) — only unauthenticated payment path in the storefront.
2. **Fix the POS Order edit discount-drop regression** (`PosQuoteScreen.tsx`) — customers are overcharged on any edited order that had loyalty/coupon applied.
3. **Harden the Refund pay-back** — multi-tender/multi-receipt ledger attribution + concurrency idempotency in `refund.ts` / `refunds/[id]/status/route.ts`.

## Security / RBAC

### 1. Razorpay order-creation endpoint has no auth and no ownership check (IDOR) — **HIGH**
- **Where:** `src/app/api/shop/orders/[id]/razorpay/route.ts:11-60`
- **Why:** Any unauthenticated caller can POST `/api/shop/orders/<anyId>/razorpay` for any `PENDING_PAYMENT` order — enumerate orders, overwrite a victim's `razorpayOrderId` to disrupt/hijack their checkout, and hammer live Razorpay order creation as an unauthenticated cost/DoS amplifier. The sibling create endpoint (`shop/orders/route.ts:26-37`) correctly calls `requirePortalCustomer()`.
- **Fix:** Call `requirePortalCustomer()` at the top and verify the resolved customer owns the order (`order.personId === customerId`, or account linkage via `resolvePortalAccountContext`) before creating the Razorpay order; return 403/404 otherwise.

### 2. Razorpay webhook accepts unsigned/forged payloads and writes to the DB — **LOW**
- **Where:** `src/app/api/shop/razorpay/webhook/route.ts:17-45`
- **Why:** No HMAC verification at all — `RAZORPAY_WEBHOOK_SECRET` is never referenced in `src/`. Anyone who learns a `razorpayOrderId` can forge a body and set `ShopOrder.razorpayPaymentId` arbitrarily. Currently "parked" (no status/GL effect, field has no reader), so blast radius is small today — but the docs (`ARCHITECTURE.md:94`, `PROJECT_BRAIN.md:216`) falsely claim the route is HMAC-verified / rejects unsigned calls.
- **Fix:** Verify HMAC-SHA256 of the raw body against `x-razorpay-signature` using `RAZORPAY_WEBHOOK_SECRET` and reject (400) before parsing/persisting, even while parked. At minimum, correct the docs so operators aren't misled.

## Accounting integrity

### 3. Refund pay-back attributes the full amount to a single cash/bank ledger — **MEDIUM**
- **Where:** `src/modules/refund/lib/refund.ts:39,102`
- **Why:** An advance can be collected across multiple tenders (cash + UPI + card) and/or multiple receipts against different till/bank ledgers, but the pay-back credits the entire refund to the first DEBIT line of the first receipt. The voucher stays balanced (so TB/BS/P&L totals are fine), but per-ledger cash/bank attribution is wrong and a real till ledger can be driven negative.
- **Fix:** Build the credit legs from the full set of tender DEBIT lines across all matching advance receipts (one Cr line per `(ledger, amount)` actually received). At minimum, when more than one tender ledger is involved, refuse the auto-post and force the manual path (the route already has a `PAYOUT_UNRESOLVED` escape hatch).

### 4. Refund pay-back has no concurrency / DB-level idempotency guard — **LOW**
- **Where:** `src/app/api/refunds/[id]/status/route.ts:44-88`
- **Why:** Idempotency rests on an in-flight read of `payoutVoucherId == null` with no transaction, no `FOR UPDATE`, and no `@unique`. Two PATCH requests racing to REFUNDED can both post a reversal PAYMENT voucher → double cash-out in the GL. Low likelihood (manual, low-volume, permission-gated; realistic trigger is a double-click).
- **Fix:** Atomically claim the refund before posting — `updateMany where payoutVoucherId is null` to set it, or wrap the read→create→mark in a serializable transaction; add `@unique` on `payoutVoucherId`.

### 5. `resolveAdvance` matches advance receipts by note substring (`contains`) — prefix collision — **LOW**
- **Where:** `src/modules/refund/lib/refund.ts:34-46`
- **Why:** Advance receipts are matched with `note contains "Advance against <ref>"`. References are zero-padded to 4 digits (`POSOD-2026-0001`), so once the per-year counter exceeds 9999, `...-1000` becomes a string-prefix of `...-10000`, and a refund on the lower-numbered order would sum and over-refund both orders' advances. Trigger is narrow (>9999 POS orders in one calendar year + adjacent numbering + refunding the prefix order).
- **Fix:** Match the note exactly (`equals`, with a delimiter that can't collide), or — better — link the receipt to the order via a real FK / `orderId` column instead of free-text matching.

### 6. EXECUTED redemption holds are never released on a post-fulfil cancel/return — **LOW** (latent)
- **Where:** `src/modules/order/lib/redemptionHold.ts:102-107`
- **Why:** `releaseRedemptions` only touches `HELD` rows, never `EXECUTED`. Harmless today — `executeRedemptions` is a documented no-op (`TODO(2b-apply)`) and no seeded transition goes from a post-fulfil stage to CANCELLED/RETURNED — but once 2b-apply actually burns loyalty/coupon/gift-card value at Fulfil, a later return of a fulfilled order will strand the reward as burned with no reversal.
- **Fix:** Track as a hard prerequisite of 2b-apply: add an EXECUTED→reversed path (un-burn loyalty lots / re-credit coupon / restore gift card) invoked on return/cancel of a fulfilled order. Keep the capture UI off until then, as the comment instructs.

## Recent-diff bugs

### 7. Editing a POS Order silently drops the loyalty/coupon discount → order total inflates — **HIGH**
- **Where:** `src/modules/pos/components/PosQuoteScreen.tsx:627-651, 765`
- **Why:** On creation, a POS Order folds loyalty redemption + coupon value into `discountAmt`/`totalAmount`. The edit path re-hydrates only `accountId/editable/lines` (and tier discount via snapshot) — the redemption and manual-coupon UI state collapse to 0. The recomputed, inflated total is saved, and since the order is the locked basis for the Sale at Fulfil, the customer is overcharged vs. the originally quoted order. The sibling POS-sale edit (`PosScreen.tsx`) preserves charges via `editMeta`; the order path has no equivalent (regression from deleting `OrderEditDialog`).
- **Fix:** On order edit, re-hydrate the saved `discountAmt/discountPct` (and shipping/roundOff) like `PosScreen`'s `editMeta` — the order GET already returns them — and carry the saved total discount through the PATCH so the previously-applied loyalty/coupon value isn't lost.

### 8. Fulfil-with-payment forwards an arbitrary client-supplied ledger id into the GL without validating it is a cash/bank ASSET account — **LOW**
- **Where:** `src/app/api/orders/[source]/[id]/fulfil/route.ts:30-36, 110-115`
- **Why:** `payments[].accountId` is forwarded verbatim into the voucher `tenders` and posted to whatever ledger is supplied — a buggy/malicious client could route collected payment to a Revenue/Liability/AR ledger, corrupting the GL/BS. The OrdersBoard UI restricts the picker, but the API is the trust boundary. Bounded by the fact the route is gated behind the privileged `accountancy:view:org` permission (not a low-priv cashier), and an invalid id fails on the Account FK.
- **Fix:** Load the supplied payment `accountId`s and assert each belongs to `CASH_IN_HAND` / `BANK_ACCOUNTS` (same check the counters route performs) before building tenders; return 400 otherwise.

### 9. `Refund.amountPaise` is `Int` but fed from `BigInt` `PosReceipt` sums — overflow on high-value advances — **LOW**
- **Where:** `prisma/schema/refund.prisma:13` (`amountPaise Int`), `src/modules/refund/lib/refund.ts:42-44`
- **Why:** `PosReceipt.amountPaise` is `BigInt`; an advance total above ~₹21.47 lakh exceeds Int32. On a Postgres integer column Prisma 7 rejects the write, so the realistic outcome is the refund-spawn (and the order Reject/Cancel transition) throwing — not silent corruption. Trigger is narrow (single order advance > ~₹21.47 lakh, then cancelled — plausible only on large B2B deals).
- **Fix:** Change `Refund.amountPaise` to `BigInt` to match `PosReceipt.amountPaise`, and update `bootstrap-seed`/`dummy-*`/`hard-clean` per the schema-seed coupling rule.

### 10. `getActiveOnlineGateway` is not filtered by environment — a TEST gateway can be returned in production — **LOW**
- **Where:** `src/shared/lib/payments/activeOnlineGateway.ts:17-23`
- **Why:** The single-winner rule (`clearOnlineSiblings`) enforces ≤1 enabled gateway *per environment*, but the resolver queries across all environments ordered by `sortOrder`, so a TEST gateway can win in production. Today the only consumer renders a "Pay online via `<name>`" display label (config-only, no live charge), so impact is cosmetic — but it becomes a mis-charge risk once the live charge lands.
- **Fix:** Filter `getActiveOnlineGateway` by the active environment (or enforce a single `enabledForOnline` across all environments in `clearOnlineSiblings`).

## Schema / seed drift

### 16. `hard-clean` leaves dummy-vouchers' non-party GL group + ledger behind (contract violation) — **LOW**
- **Where:** `prisma/seeds/dummy-vouchers.ts:46-58`
- **Why:** After `pnpm seed:hard-clean`, the dummy-only "Courier & Shipping Cost Pool" `AccountGroup` and "DTDC Counter" GL ledger survive (Phase 2 only deletes `Account` rows with non-null party), and `OrgDefaults.shippingPoolGroupId` stays pointed at the surviving group — so the DB is not at bootstrap state, violating hard-clean's stated contract. Dev-only, disposable DB, idempotent on re-seed → low impact.
- **Fix:** In `hard-clean.ts` after Phase 2, also `DELETE FROM "Account" WHERE name = 'DTDC Counter'`, `DELETE FROM "AccountGroup" WHERE name = 'Courier & Shipping Cost Pool'`, and `UPDATE "OrgDefaults" SET "shippingPoolGroupId" = NULL` (mirror the existing "Difference in Opening Balances" cleanup at lines 171-174).
