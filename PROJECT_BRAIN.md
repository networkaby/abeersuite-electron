> Internal business OS for a multi-channel computer & CCTV shop — retail (in-store + online), wholesale, and a repair service centre on one shared inventory and accounting backbone.

**Stack:** Next.js 16.2.3 (App Router, Turbopack), React 19, PostgreSQL (Supabase), Prisma 7.7.0 (split schema), NextAuth v5 beta (JWT), Tailwind v4, shadcn/ui, Zustand 5, Sonner, Axios, React Hook Form, Zod, Razorpay, Cloudinary, Sentry.

## 🎯 Goal

Replace paper/spreadsheets across the whole business with one app:

- **Repair tickets** — Received → Diagnosing → Repairing → … → Returned, with role handoffs (Front Desk, Technician, Despatch, Admin).
- **Accounting** — Tally-style GL: vouchers, GST/HSN, BS / P&L / Day Book / Trial Balance, audit trails.
- **Unified inventory** — one `InvProduct` master feeds storefront, repair, POS, wholesale.
- **POS** — counter-based tills, shift lifecycle, sale returns.
- **CRM & leads** — kanban pipeline reusing the Ticket engine.
- **Customer shop + portal** — `/shop` + `/portal` (separate `CustomerPortalCredential` auth).
- **Org / RBAC** — multi-branch, multi-department, rank-gated roles with `area:operation:scope` permissions.

- **2026-09-02 — The DB decides who holds a counter, and a closed shift stays closed**. Releasing a counter is a **device swap, not a cash event**: the PC dies, the admin moves the counter to another machine, and the shift and drawer carry on. Four things stopped that from working. (1) The shift-open route's three reads were commented "Authoritative" and called `prisma` — the replica on a counter PC — so a replacement PC's own replica still showed the old lock and refused the open, which is the exact moment the swap has to work; they now use `prismaAuthoritative` ([`shifts/route.ts`](src/app/api/pos/shifts/route.ts)). (2) [`reconcileCounterSetup`](src/shared/lib/counter/setupGate.ts) asked the replica-backed counter list whether this PC still held its counter — circular, since that row is the one this machine stamps at shift open; it now asks the new [`/api/pos/counters/my-binding`](src/app/api/pos/counters/my-binding/route.ts), which reads authoritatively. Unreachable still means "trust the local file", so a blip never signs anyone out. (3) `release-mine` wrote the release into the replica, where the push then **undid** it — the PC believed it had let go while the DB never agreed; it is authoritative now, and fails loudly when Supabase is unreachable rather than writing a lie. (4) New nullable **`PosCounter.releasedAt`**: `boundDeviceId = null` alone cannot distinguish "released" from "never claimed", and this table carries no `updatedAt` for last-write-wins to arbitrate with, so a counter that was offline when it was released woke up, pushed its queued row and **silently took itself back**. [`reconcileCounterBinding`](src/shared/lib/sync/push.ts) now refuses a bind older than the stamp; that PC must run the setup wizard and take a new counter number. Bind clears the stamp. Separately, a `pos_shifts` write is **dropped when the DB already says CLOSED** — blind LWW would either overwrite the admin's declared cash and variance with a second closing Contra (the same cash swept to the vault twice) or drop the local close silently — and [`shifts/current`](src/app/api/pos/shifts/current/route.ts) confirms the replica's OPEN answer against the DB by primary key, so a machine recovering from a force-close is offered a **fresh shift** rather than handed one the office has settled. Force-close remains rare and by the counter's own request; recovery is the counter's job. Known residual: drops/expenditures/receipts minted offline *after* a force-close still carry the old `shiftId` and land on the closed shift, visible for audit rather than moved automatically. Schema: one additive nullable column, mirrored in [`localDbProvisioner`](electron/localDbProvisioner.ts)'s column migrations and omitted from the personal snapshot (it is runtime state, not config). Verified: `tsc --noEmit` clean, sync registry and local schema regenerated.

- **2026-08-28 — Counter goes local-first, behind two independent dials. Five separate faults meant the offline path had never once worked end to end.** Owner decision: a counter should use its own PostgreSQL the way the web app uses Supabase, with replica pull and outbox push as a separate background concern. Rolling out to 2–3 mostly-online counters; long-offline and adversarial-conflict correctness is explicitly deferred.
  - **What was broken.** Each of these alone was sufficient. (1) `applyIdRanges` connected on the URL `main.ts` handed it, which is the `smx_app` role — no `CREATE ON SCHEMA`, no sequence ownership — so both its `CREATE TABLE "_id_ranges"` and its `ALTER SEQUENCE` failed; reproduced against a real cluster as *permission denied for schema public* and *must be owner of sequence*. (2) Those errors were swallowed, so `isOfflineRangeApplied()` read the missing table as "no confirmed range" and blocked every offline write on the machine, silently. (3) **8 of the 11 hand-written sequence names did not exist** — Prisma names a sequence after the TABLE, so only the `@@map`'d POS ones were real; `universal_vouchers_id_seq`, `voucher_details_id_seq` and `tickets_id_seq` are fiction, and the first `ALTER` would have aborted the batch anyway. (4) [`electron/outboxFlusher.ts`](src/shared/lib/sync/flusher.ts) POSTed to `/api/sync/push` from the Electron main process, which holds no session cookie, so `requireAuth()` answered 401 every time — and its `catch` was empty, so nothing was ever logged. (5) Three models had outbox entries but were missing from the 36-model write allowlist so their writes threw, while **27 models were in the allowlist with no outbox entry** — products, customers, accounts, stock ledger, loyalty ledger — so those writes succeeded locally and never reached the cloud.
  - **Writes are captured by Postgres triggers, not app code.** One `AFTER INSERT OR UPDATE` trigger per replicated table, generated into [`resources/local-schema.sql`](scripts/gen-local-schema.ts) from `prisma/sync-tables.json`, so the set cannot drift from the schema (a `--check` fails the build if triggers ≠ registry tables). It records `to_jsonb(NEW)` — the committed row, not `args.data` — plus `row_key` as jsonb, which carries compound primary keys with their types intact. The old interceptor missed `createMany`, `upsert`, nested writes and raw SQL entirely; the trigger cannot be bypassed by any of them. **Echo suppression is free**: the sync worker writes pulled rows under `SET LOCAL session_replication_role = replica`, and Postgres fires only REPLICA/ALWAYS triggers in that mode — so ordinary triggers do not re-queue what was just pulled down. Verified non-vacuously: 4 writes made in replica mode landed and produced **zero** outbox rows, while the same tables written normally were captured.
  - **`_outbox.id` order is a valid foreign-key order**, which is what lets the pusher replay without a topological sort: local FKs are enforced immediately, so when a child was written its parent was already visible — hence committed earlier, hence a lower id. That argument needs `ORDER BY id` (the previous `created_at` is transaction *start* time and can invert between overlapping transactions) and a run that **stops at the first failure**. Stopping is only safe because `_outbox` gained backoff and a dead letter — without one, a single poison row would block every later mutation forever, visible only as a pending count that never fell.
  - **Id ranges now cover all 79 autoincrement models, discovered from `pg_depend`** rather than a hand-kept list of 11. Under local-first the counter writes all 79, and an unreserved sequence mints from 1 — which does not crash, it makes the push upsert over an unrelated cloud row. The privileged half moved into `_apply_id_range()`, `SECURITY DEFINER` and owned by `postgres`, so the app role gets `EXECUTE` and not the `DROP`/`ALTER` that sequence ownership would imply. It also never moves a sequence backwards, so re-applying after ids have been minted is a no-op instead of reissuing them.
  - **Two dials.** `READ_MODE` (live|shadow|local) decides reads; new `WRITE_MODE` (live|local) decides writes. **WRITE_MODE picks the base client, READ_MODE decides whether reads are redirected off it** — that order matters, because a `$transaction` is a write, so it opens on the WRITE_MODE client and every read inside it stays on the same database. Both default to `live`, so a counter setting neither is unchanged, and `WRITE_MODE=live` is the escape hatch: one env var reverts a misbehaving till without a rebuild. The offline voucher-type policy is now conditional on that fallback — under `local` it would refuse those types permanently rather than protect anything.
  - **`prismaLive` now means Supabase and only Supabase.** It previously redirected reads to the replica like everything else, which on the push path would have been live data loss: the last-write-wins check would have read the counter's own just-written row from the replica, concluded the cloud was newer, and dropped the mutation as superseded. `prismaRead` is deleted (zero consumers); `prismaAuthoritative` keeps 4 sites across the two counter-**admin** flows, where each read gates a decision to REFUSE.
  - **First-boot gate.** An empty replica does not error, it returns fewer rows — a product list renders blank, which reads as "those were deleted". [`waitForReplica.ts`](electron/waitForReplica.ts) holds the splash until `_sync_status.ready`, showing real `tables_synced`/`tables_total` progress; [`ReplicaReadyGate`](src/shared/components/ReplicaReadyGate.tsx) covers a replica that goes unready mid-session, and is conditional on `READ_MODE ≠ live` because not-ready is the ordinary state on a counter that reads live.
  - **Still open.** Row-ownership on `/api/sync/push` (any authenticated session can address any row in a syncable table). The scripted end-to-end harness — provision, first sync, exercise each write class, pull the network, restore, compare row-for-row with `verify-replica.js`.

- **2026-07-29 — Ledger reconciliation flag, with an automatic retreat on backdated entries**. A reconciliation is a human assertion made _later_ than the period it covers: you sit down on 27-Dec and confirm the statement through 15-Oct. So the flag is stored as two dates that mean different things — [`Account.reconciledThrough`](prisma/schema/accounts.prisma) (`@db.Date`, the business watermark) and `reconciledAt` (the wall-clock instant a human did the check), plus `reconciledById`. **The gap between them is a hole**: a voucher dated 13-Oct entered on 29-Dec lands inside an already-certified window and silently changes a balance that was signed off, while the flag keeps reading "through 15-Oct". Neither hard-blocking the post (backdated entries are legitimate) nor leaving the flag to lie is acceptable, so the rule is **retreat**: the watermark drops to the day _before_ the dirty entry — 13-Oct dirty → watermark falls to **12-Oct**, putting 13/14/15-Oct back into unreconciled territory. The 14th and 15th weren't touched individually, but they were certified as one block _with_ the 13th, so the block needs re-confirming. `reconciledAt` is deliberately **not** restamped by a retreat — nobody reconciled on 29-Dec, and overwriting it would invent a reconciliation that never happened. One shared helper [`retreatReconciliation()`](src/modules/accountancy/lib/reconciliation.ts) does the whole job in a single `updateMany` (the new watermark depends only on the voucher's date, and a `gte` filter leaves ledgers reconciled to an earlier date alone), called inside the caller's transaction so it can never survive a rolled-back posting. Wired at **four** write points, not one: both paths a spine can reach POSTED by — `engineGlArm` (covering its ATTACH and CREATE branches alike) and `enginePostSpine` (the `engineCreateVoucher` path) — and all three **hard-delete** routes, since removing a posted voucher dirties a window exactly as much as adding one. - **2026-07-27 — Negative stock is valued NEGATIVELY (Tally convention), not clamped to ₹0**. Exposed by the as-at-date work above. ## 🧭 Design: Workflow engine — the Worker model (agreed 2026-06-13)

The whole ticket/CRM/order workflow engine reduces to one small, repeatable shape. A **Pipeline** is an ordered set of **Workers**; an entity riding the shared `Pipeline`/`TicketStatus` spine (Ticket / Task / Deal / Order) sits on one Worker at a time and moves along configured edges.

**A Worker = state + one executor + routing + retry.** Nothing more — the earlier "6 powers" framing was a mirage.

- **State** — where the entity sits (the Worker is the sub-status, renamed `TicketSubStatus → TicketWorker` on 2026-06-13).
- **Executor — exactly one, a person _or_ a machine** ("one worker, one thing"):
  - **Human Work** — permission-gated (`work:<id>`); surfaces the entity in the **Work Inbox** (`/office/work-flow-inbox`) for whoever holds the permission. For activities that _can't_ be automated — packaging, physical QC, handing the device over, an in-person call. The person does it and records **Success / Unsuccess**.
  - **Action (automated)** — the system performs it: send email, create a deal/order/sale, spawn a child entity. For activities that _can_ be automated. Dispatched through an `ACTION_REGISTRY` (same shape as `childEntities.ts`).
  - The human-vs-action choice lives on the **Work** (W1–W8): each Work is _either_ a human activity _or_ an automated action ("different action for different work"). A Worker just _places_ one Work at one point in a pipeline.
- **Routing** — every Worker exits the same way: `Success → <worker>` / `Unsuccess → <worker>`. **The engine never branches on executor type** — a human clicking the outcome and an action reporting its result feed the identical routes.
- **Retry** — for _waiting_ executors (a human follow-up loop, or an action polling an external result): the front-loaded `retrySchedule` re-arms attempts and drops the entity into the Inbox **Waiting** tab until due.

**Composition is by chaining, not flags.** "Auto-email, then a human confirms the reply" = two Workers in sequence: `[Action: Email] → success → [Human: Confirm reply]`. The pipeline is the composition; each Worker stays atomic.

**Spawn was never a special power — it's the first Action.** "Create a child ticket/deal/order on another pipeline" (the polymorphic spawn shipped 2026-06-13) is just `action(spawn, <pipeline>)`. The old powers list (route / retry / triggerMap / spawn / action) collapses to: _one Work (human or action) + routing + retry._

**How an Action reports its outcome** (the machine equivalent of the human button):

- **Sync action** (email sent, customer row created) → returns success/fail immediately → routes now.
- **Async action** (waiting on an external result — a courier status, an email reply, a spawned child terminating) → the Worker parks as **waiting**; the outcome arrives later via callback/signal and _then_ fires the route. This is exactly the spawn's existing report-back: a child Worker carrying a `parentSignal` ("success"/"fail") resolves the parent. **Async actions = `parentSignal`, generalized.**

**When is a Work "done"?** When its executor produces an outcome — a human work when the person records Success/Unsuccess; a sync action when the handler returns; an async action when its signal/callback arrives (or it exhausts its retry schedule). Until then the Worker is _in progress_, or _waiting_ if snoozed.

**Context — what a worker collects and hands on.** A completion isn't just an outcome; it can also produce **data**. Each Work carries a small, configurable **field schema** (kinds: `text · number · money · date · entity-ref`) — and the data runs a four-step lifecycle:

- **Collect** — a human work renders those fields as a **mini-form in the completion dialog** (replacing reliance on the free note); an action **produces** them (email → message-id, payment → ref).
- **Carry** — the values ride **`Ticket.context`** (the JSON bag already on the ticket), keyed, readable by downstream workers on the same ticket.
- **Pass** — a spawn **maps parent context → the child** entity (any pipeline), so a spawned _Tracking_ entity is born already knowing the `trackingId`. (The old "configurable spawn context" idea is _only_ this step.)
- **Render** — an activity/title **template** turns the fields into human text — _"Letter posted to President · India Post · #EX123IN"_, not _"mail sent"_ — so anyone reads "what and where".

Typed fields are **mandatory where a downstream worker can't function without an input** (Issue-Charger needs `neededPart`; Track-Letter needs `trackingId`); the free-text note stays as the unstructured catch-all. Kept to a small field-kind set, not a form-builder. So a Work = **executor** (who/what does it) + **context schema** (what data it collects/carries/passes/renders) — see Next-up / task list.

**The money/workflow boundary (hard constraint).** The workflow is **disposable and fully data-configurable**; the **accounting core is ACID and protected**. Actions are the bridge — but a money action **stages or opens a flow prefilled; it never silently posts a GL entry.** So actions sit on a spectrum: fully-auto (email, spawn) → one-click (create deal) → **staged-with-human-confirm (sale/order/voucher)**. Integrations (dial/email/WhatsApp) start as safe stubs (`tel:`/`mailto:` + a logged activity) behind provider config, real providers wired later.

## 🧭 Design: Permissions — three-axis model (agreed 2026-07-03)

The RBAC rethink. Old model was one tangled grid — `module × action × scope` (e.g. `accountancy:edit:branch`) — which mixed three unrelated questions into a single permission row. The new model splits them into **three independent axes**, all **sourced from the position** (the appointment), never stapled to the person. A person = a bundle of positions; every effective value is a **union over their positions**.

**Axis 1 — UI (which surfaces you get).** Give each position a customised UI; hide the irrelevant. Driven by `ui:sidebar:*` grants, generated from the constants file (WORKSPACE_NAV + MODULE_SECTIONS + ADMIN_NAV + SETTINGS_NAV). A nav grant = "you get this page, may open it, and may load its data." Coarse on/off per nav item, full depth. **Built** (sidebar authoritative + constants-driven). Note (2026-07-13): reads no longer gate on `requireModuleAccess` — GET routes + page views are plain `requireAuth`; nav grants drive _visibility_, not API read access.

**Axis 2 — Action (what you can do inside).** The finer matrix, once you are on a surface. Two _sub-flavours_ that default in **opposite directions**:

- **Read / content-visibility** → default **OPEN**, restrict _down_. A nav grant implies you may read everything on the surface; a per-kind `view`/`open` un-tick _hides_ a kind. (Answer to "has Day Book, can he see Payment?" → **yes by default**.) Stored additively (nav auto-implies view on all kinds; un-tick removes) so we never run two opposite mechanics. **Built (2026-07-13):** every GET API + page/layout/nav view is default-open (`requireAuth`) — the hidden capability gates were swept out. Remaining: the per-kind `view`/`open` un-tick to hide a _specific_ kind on a shared surface.
- **Write / act** → default **DENIED**, grant _up_. Seeing a tool never implies mutating with it. Per-kind voucher `create/post/cancel/delete`, and tool actions like a future `pricing:modify`. (Answer to "has pricing-strategy, can he modify price?" → **no by default** — a separate grant.) **Building** (per-kind voucher matrix exists; View/Open columns added; enforcement on the write side + report filtering pending).

**Axis 3 — Radius (whose records, across which branches).** A property of the **position's posting**, not the person, and not a permission suffix:

- **Own branch** — baseline, no grant needed; it's just the branch of your position.
- **Multi-branch** — holding positions in several branches → the **union** of those branches (`branchIds`, resolved at login).
- **All-branch (executive)** — one position carries an `access:all-branches` grant that lifts the branch fence entirely.

Data queries filter by the resolved branch set (`where.branchId in branchIds`), skipped when the all-branch grant is present. This **replaces the `:own / :branch / :org` suffix** — the old grid's scope dimension collapses to just "my branches vs all branches", carried by postings + one grant, so the `scope` enum's finer gradations (`OWN/TEAM/DEPARTMENT/REGION`) are no longer needed as a radius system.

**Migration stance.** The old `module × action × scope` permissions (the `accountancy:create:own` etc. grid) have **no distinct job left** — Axis 1 replaced `view`, the per-kind matrix replaced `create/edit/delete`, postings replaced the scope suffix. They survive **only as `newCheck OR oldCapability` fallbacks** so nothing breaks mid-migration. **Do not build new roles on them.** Retire them (seeds + `OR` fallbacks) in the cleanup pass once Axis-2 write enforcement + Axis-3 branch filtering are wired. See memories `sidebar-visibility-permissions`, `develop-new-then-cleanup`.

## ⚠️ Known gotchas

- **Server restart required after `prisma generate`.** Turbopack caches Prisma client chunks.
- **Middleware is `src/proxy.ts`, NOT `middleware.ts`.** Next.js 16 rename.
- **Split Prisma schema** — `prisma/schema/*.prisma`, configured in `prisma.config.ts`.
- **NextAuth v5 beta** — cast `session.user` for `id`/`role`/`roles`/`permissions`. Never use `getToken()`.
- **Scalar list filtering** — `String[]` uses `{ has: "R3" }` (Postgres only).
- **Worker `allowedRoles`** — R1 always bypasses, by design.
- **Opaque IDs** — S1–S10 statuses, SS1–SS37 workers, R1–R4 roles, P1–P4 priorities, `P-REPAIR` / `P-SALES` pipelines.
- **`@@unique` with nullable fields** — Postgres treats NULL as distinct; `skipDuplicates` is unreliable. Use `findFirst` + `create`.
- **Razorpay** — `RAZORPAY_WEBHOOK_SECRET` must be set in `.env`, otherwise webhooks reject silently.
- **Portal and staff auth never crossover.** Don't reuse staff cookies for portal.
- **Shop prices in paise.** Use `moneyInr.ts` to format. Never divide by 100 inline.
- **Schema added via `db push`, no migration**: GST/HSN columns, naming-convention columns. Migrate before any prod deploy.
- **Legacy `src/modules/tally/`** co-exists with `src/modules/accountancy/`. Rename was 2026-05-07; folder removal is pending separate work.
- **POS operator access = `ui:sidebar:workspace:pos`, NOT `ui:sidebar:pos:*`.** The office `pos` module (`ui:sidebar:pos:*` = Shift Reports / Counters, manager-facing) is a _separate_ grant from the operator's Workspace → POS link. POS **write** routes gate on `requirePosVoucher` (the `pos:voucher:create:<kind>` tick), never `requireModuleAccess("pos")` — else a pure counter operator 403s on checkout even with an open shift. (Fixed 2026-07-13.)
- **Reads are default-open; don't re-add read gates.** Since 2026-07-13, GET APIs + page/layout/nav views take only `requireAuth`. A restriction must be a role-page tick (sidebar visibility or a write permission) or branch radius — nothing else. New read-gating is a _deliberate, parked_ follow-up, not something to reintroduce route-by-route.
- **Date-field vocabulary in reports: "Opening" = start of day, "Closing" = end of day.** In any `from`↔`to` range, `from` is pinned to start-of-day and `to` to end-of-day (`startOfDayUtc`/`endOfDayUtc` in [period.ts](src/modules/accountancy/lib/period.ts)) — so `from` = opening of that day, `to` = closing of that day, both inclusive. Report **"As at"** fields (Balance Sheet) are **closing** balances inclusive of that date's vouchers (`parseAsOf` also uses `endOfDayUtc`).
- **Ledger opening balance / product opening stock is universal — no date field at all (decided 2026-07-28).** `Account.openingBalance(Type)` and `InvProduct.openingStock/openingRate` are always effective from the start of the books, whether the row was imported from another system or created fresh — no per-account/per-product cutover date, ever. The `openingBalanceDate`/`openingStockDate` **columns still exist** (nullable, unused) because every read path already treats null as "always applies" (`aggregateLedger.ts`, `valuation.ts`, `costBasis.ts`, `balance.ts`) — so this was a pure UI/API removal, not a schema change. The date input was removed from every entry point (ledger/product opening-balance forms, the Add-Ledger/Add-Product quick-create dialogs, the customer/product CSV importers, the merge-duplicate-party flow) and every write API now hardcodes the date column to `null`. **Do not re-add a per-row opening date field** — if staged/staggered migration cutover is ever needed again, that's a new, deliberately-scoped feature, not a revival of this one. Leftover non-null values in the live DB are cleared by a one-off script — see `prisma/seeds/migrate-clear-opening-dates.ts`.
- **Departments are intentionally cosmetic for now (decided 2026-06-23).** They structure the org chart and derive `user.departmentIds`, but nothing user-facing keys off them. The home dashboard ([office/page.tsx](<src/app/(protected)/office/page.tsx>)) was switched from department-routed briefings to a **common, permission-gated** dashboard — every user sees the same page and each briefing card shows by permission (admin:bypass sees all), reusing the same `DeptBriefings.tsx` components. **Department-scoped data visibility is also deferred**: the `*:department` permission keys (`tickets/customers/assignments:*:department`) and the `department` tier in [ticketScope.ts](src/modules/repairing/lib/ticketScope.ts) are real code but **granted to no role**, so the filter never fires. All of this is by design, not a bug — do **not** wire dept-scoped silos or dept-routed UI until the department feature is built. Branch is the enforced scope (GL / POS / vault).
