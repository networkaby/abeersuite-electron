> Internal business OS for a multi-channel computer & CCTV shop — retail (in-store + online), wholesale, and a repair service centre on one shared inventory and accounting backbone.

**Stack:** Next.js 16.2.3 (App Router, Turbopack), React 19, PostgreSQL (Supabase), Prisma 7.7.0 (split schema), NextAuth v5 beta (JWT), Tailwind v4, shadcn/ui, Zustand 5, Sonner, Axios, React Hook Form, Zod, Razorpay, Cloudinary, Sentry.

## 🎯 Goal

Replace paper/spreadsheets across the whole business with one app:

- **Repair tickets** — Received → Diagnosing → Repairing → … → Returned, with role handoffs (Front Desk, Technician, Despatch, Admin).
- **Accounting** — Tally-style GL: vouchers, GST/HSN, BS / P&L / Day Book / Trial Balance, audit trails.
- **Unified inventory** — one `InvProduct` master feeds storefront, repair, POS, wholesale.
- **POS** — counter-based tills, shift lifecycle, sale returns.
- **CRM & leads** — kanban pipeline reusing the Ticket engine.
- **Customer shop + portal** — `/shop` + `/portal` (separate `CustomerPortalCredential` auth).
- **Org / RBAC** — multi-branch, multi-department, rank-gated roles with `area:operation:scope` permissions.

## 🧭 Design: Workflow engine — the Worker model (agreed 2026-06-13)

The whole ticket/CRM/order workflow engine reduces to one small, repeatable shape. A **Pipeline** is an ordered set of **Workers**; an entity riding the shared `Pipeline`/`TicketStatus` spine (Ticket / Task / Deal / Order) sits on one Worker at a time and moves along configured edges.

**A Worker = state + one executor + routing + retry.** Nothing more — the earlier "6 powers" framing was a mirage.

- **State** — where the entity sits (the Worker is the sub-status, renamed `TicketSubStatus → TicketWorker` on 2026-06-13).
- **Executor — exactly one, a person *or* a machine** ("one worker, one thing"):
  - **Human Work** — permission-gated (`work:<id>`); surfaces the entity in the **Work Inbox** (`/office/core/assignments`) for whoever holds the permission. For activities that *can't* be automated — packaging, physical QC, handing the device over, an in-person call. The person does it and records **Success / Unsuccess**.
  - **Action (automated)** — the system performs it: send email, create a deal/order/sale, spawn a child entity. For activities that *can* be automated. Dispatched through an `ACTION_REGISTRY` (same shape as `childEntities.ts`).
  - The human-vs-action choice lives on the **Work** (W1–W8): each Work is *either* a human activity *or* an automated action ("different action for different work"). A Worker just *places* one Work at one point in a pipeline.
- **Routing** — every Worker exits the same way: `Success → <worker>` / `Unsuccess → <worker>`. **The engine never branches on executor type** — a human clicking the outcome and an action reporting its result feed the identical routes.
- **Retry** — for *waiting* executors (a human follow-up loop, or an action polling an external result): the front-loaded `retrySchedule` re-arms attempts and drops the entity into the Inbox **Waiting** tab until due.

**Composition is by chaining, not flags.** "Auto-email, then a human confirms the reply" = two Workers in sequence: `[Action: Email] → success → [Human: Confirm reply]`. The pipeline is the composition; each Worker stays atomic.

**Spawn was never a special power — it's the first Action.** "Create a child ticket/deal/order on another pipeline" (the polymorphic spawn shipped 2026-06-13) is just `action(spawn, <pipeline>)`. The old powers list (route / retry / triggerMap / spawn / action) collapses to: *one Work (human or action) + routing + retry.*

**How an Action reports its outcome** (the machine equivalent of the human button):
- **Sync action** (email sent, customer row created) → returns success/fail immediately → routes now.
- **Async action** (waiting on an external result — a courier status, an email reply, a spawned child terminating) → the Worker parks as **waiting**; the outcome arrives later via callback/signal and *then* fires the route. This is exactly the spawn's existing report-back: a child Worker carrying a `parentSignal` ("success"/"fail") resolves the parent. **Async actions = `parentSignal`, generalized.**

**When is a Work "done"?** When its executor produces an outcome — a human work when the person records Success/Unsuccess; a sync action when the handler returns; an async action when its signal/callback arrives (or it exhausts its retry schedule). Until then the Worker is *in progress*, or *waiting* if snoozed.

**Context — what a worker collects and hands on.** A completion isn't just an outcome; it can also produce **data**. Each Work carries a small, configurable **field schema** (kinds: `text · number · money · date · entity-ref`) — and the data runs a four-step lifecycle:
- **Collect** — a human work renders those fields as a **mini-form in the completion dialog** (replacing reliance on the free note); an action **produces** them (email → message-id, payment → ref).
- **Carry** — the values ride **`Ticket.context`** (the JSON bag already on the ticket), keyed, readable by downstream workers on the same ticket.
- **Pass** — a spawn **maps parent context → the child** entity (any pipeline), so a spawned *Tracking* entity is born already knowing the `trackingId`. (The old "configurable spawn context" idea is *only* this step.)
- **Render** — an activity/title **template** turns the fields into human text — *"Letter posted to President · India Post · #EX123IN"*, not *"mail sent"* — so anyone reads "what and where".

Typed fields are **mandatory where a downstream worker can't function without an input** (Issue-Charger needs `neededPart`; Track-Letter needs `trackingId`); the free-text note stays as the unstructured catch-all. Kept to a small field-kind set, not a form-builder. So a Work = **executor** (who/what does it) + **context schema** (what data it collects/carries/passes/renders) — see Next-up / task list.

**The money/workflow boundary (hard constraint).** The workflow is **disposable and fully data-configurable**; the **accounting core is ACID and protected**. Actions are the bridge — but a money action **stages or opens a flow prefilled; it never silently posts a GL entry.** So actions sit on a spectrum: fully-auto (email, spawn) → one-click (create deal) → **staged-with-human-confirm (sale/order/voucher)**. Integrations (dial/email/WhatsApp) start as safe stubs (`tel:`/`mailto:` + a logged activity) behind provider config, real providers wired later.

**Status.** Shipped (2026-06-13): polymorphic child-entity spawn + `TicketWorker` rename. Pending: the `ACTION_REGISTRY` + `Work.actionType` (+ optional per-Worker config) — first slice = **Dial** on W1 Tele Calling (additive, no DB reset). Folds into the configurable-spawn work (Next-up item 6) and memory `workflow-access-work-layer-redesign`.

## ⚠️ Known gotchas

- **Server restart required after `prisma generate`.** Turbopack caches Prisma client chunks.
- **Middleware is `src/proxy.ts`, NOT `middleware.ts`.** Next.js 16 rename.
- **Split Prisma schema** — `prisma/schema/*.prisma`, configured in `prisma.config.ts`.
- **NextAuth v5 beta** — cast `session.user` for `id`/`role`/`roles`/`permissions`. Never use `getToken()`.
- **Scalar list filtering** — `String[]` uses `{ has: "R3" }` (Postgres only).
- **Worker `allowedRoles`** — R1 always bypasses, by design.
- **Opaque IDs** — S1–S10 statuses, SS1–SS37 workers, R1–R4 roles, P1–P4 priorities, `P-REPAIR` / `P-SALES` pipelines.
- **`@@unique` with nullable fields** — Postgres treats NULL as distinct; `skipDuplicates` is unreliable. Use `findFirst` + `create`.
- **Razorpay** — `RAZORPAY_WEBHOOK_SECRET` must be set in `.env`, otherwise webhooks reject silently.
- **Portal and staff auth never crossover.** Don't reuse staff cookies for portal.
- **Shop prices in paise.** Use `moneyInr.ts` to format. Never divide by 100 inline.
- **Schema added via `db push`, no migration**: GST/HSN columns, naming-convention columns. Migrate before any prod deploy.
- **Legacy `src/modules/tally/`** co-exists with `src/modules/accountancy/`. Rename was 2026-05-07; folder removal is pending separate work.
- **Departments are intentionally cosmetic for now (decided 2026-06-23).** They structure the org chart and derive `user.departmentIds`, but nothing user-facing keys off them. The home dashboard ([office/page.tsx](src/app/(protected)/office/page.tsx)) was switched from department-routed briefings to a **common, permission-gated** dashboard — every user sees the same page and each briefing card shows by permission (admin:bypass sees all), reusing the same `DeptBriefings.tsx` components. **Department-scoped data visibility is also deferred**: the `*:department` permission keys (`tickets/customers/assignments:*:department`) and the `department` tier in [ticketScope.ts](src/modules/repairing/lib/ticketScope.ts) are real code but **granted to no role**, so the filter never fires. All of this is by design, not a bug — do **not** wire dept-scoped silos or dept-routed UI until the department feature is built. Branch is the enforced scope (GL / POS / vault).
